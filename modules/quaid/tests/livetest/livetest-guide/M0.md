# M0: Agent-Driven Install

Purpose: validate that the installer correctly provisions a Quaid workspace, identity files, config,
database, and hooks from scratch — driven by the platform agent reading the AI install guide, not by
ad-hoc coordinator commands. Running any subsequent milestone against a hand-crafted or pre-existing
workspace does NOT test the installer; the reinstall is mandatory every run.

## Preconditions (handled by preflight)

Before M0 runs, `livetest-preflight.sh` has already:
- wiped `~/.quaid`, the OC plugin extension dir, and the per-platform caches on the remote
- rsynced the current dev tree to the remote
- seeded the shared Quaid auth credential and the CC `claude` CLI credential
- started the platform services

Do not run install commands yourself before M0 — the whole point is that the platform agent does it.

## Lane order

Only one platform runs its M0 install at a time (install is sequential; testers serialize themselves
via the coordinator). Once a platform's M0 passes, the next platform's tester starts its M0. Once
all lane M0s pass, parallel M1+ execution begins.

## Tester procedure

1. **Dry-run the installer** to validate the plan before handing off. Do not set `QUAID_INSTANCE` —
   instances are path-derived on first use (`/tmp/cc-livetest` →
   `claude-code-private-tmp-cc-livetest`, `/private/tmp/cdx-livetest` →
   `codex-private-tmp-cdx-livetest`, OC → `openclaw-main` from agent config).

   ```bash
   # OC tester
   ssh REMOTE_HOST 'source ~/.zprofile >/dev/null 2>&1; cd ~/quaidcode/dev && QUAID_ALLOW_DEV_INSTALL=1 node setup-quaid.mjs \
     --dry-run --adapter openclaw --owner-name OWNER_NAME --agent 2>&1 | tail -40'

   # CC tester
   ssh REMOTE_HOST 'source ~/.zprofile >/dev/null 2>&1; cd ~/quaidcode/dev && QUAID_ALLOW_DEV_INSTALL=1 node setup-quaid.mjs \
     --dry-run --adapter claude-code --owner-name OWNER_NAME --agent 2>&1 | tail -40'

   # CDX tester
   ssh REMOTE_HOST 'source ~/.zprofile >/dev/null 2>&1; cd ~/quaidcode/dev && QUAID_ALLOW_DEV_INSTALL=1 node setup-quaid.mjs \
     --dry-run --adapter codex --owner-name OWNER_NAME --agent 2>&1 | tail -40'
   ```

   Check the plan output: `platform` matches your lane, hidden Quaid home is `~/.quaid`, visible is
   `~/quaid`, `instanceId` is the expected path-derived id, no fatal errors.

   If not the first platform installed this run, add `--add-platform` (legacy: `--add-instance`). If
   the installer rejects `--add-platform`, fall back to `--add-instance` once and route the gap as
   an installer bug.

2. **Hand off to the platform agent** with the install message:

   > Please install Quaid by following the local AI install guide exactly, including its mandatory
   > first command: `~/quaidcode/dev/docs/AI-INSTALL.md`
   >
   > Use these parameters:
   > - Adapter/platform: PLATFORM
   > - Owner name: OWNER_NAME
   >
   > Quaid uses a fixed split layout: hidden `~/.quaid` plus visible `~/quaid`. Do not choose or
   > pass a custom workspace path. The guide path is inside the local main checkout — use that
   > checkout directly. Do not browse the web for install docs or source during M0. Do not install a
   > release build or any non-main branch.
   >
   > Tell me when Quaid is installed and `quaid doctor` returns healthy.

3. **Wait** for the platform agent to report complete. Do not try to help it unless it posts an
   error. **Do not provide specific installer commands** — the platform reads the guide and figures
   out the steps. Answer clarifying questions naturally. If the platform cannot complete the install
   after reasonable attempts, post an ISSUE to the coordinator — do not run the install yourself.

4. **Handle installer credential prompts.** If the installer exits with an "Action Needed" note
   about a missing credential (auth token, API key, etc.), this is expected and not a failure. The
   correct response is:

   a. Read the instructions in the note — the installer prints the exact steps needed (what command
      to run, where to write the file).
   b. Relay them to the user verbatim. Do not paraphrase. Tell them clearly: what to run in a new
      terminal, where to write the result, and that they should NOT paste the credential into this
      conversation.
   c. Wait for the user to confirm the credential has been written.
   d. Re-run the installer using the same parameters. The installer will find the file and continue.

   The installer always prints the exact file path — use that path, not a hardcoded one.

5. **Verify install quality** per your platform supplement and the checks below.

## Pass criteria

**M0 PASS:** platform self-installed from `main` AND pre-install survey visible AND install messages
visible AND `quaid doctor` healthy.

**M0 FAIL:** platform could not install, silent install, or `quaid doctor` errors. Post an ISSUE to
the coordinator mailbox with the full platform pane capture.

Concrete checks:

- `quaid doctor` returns healthy (exit 0, no CRITICAL warnings).
- Install artifacts exist at expected paths:
  - `~/.quaid/instances/<instance_id>/data/memory.db` (sqlite, non-empty after first hook).
  - `~/.quaid/plugins/quaid/` (or, for OC, `~/.openclaw/extensions/quaid/`).
  - Hook registrations in the platform's config: CC `~/.claude/settings.json`, CDX
    `~/.codex/hooks.json`, OC `openclaw.json` plugin slot.
- Basic agent turn succeeds without hanging.
- No orphan install lock (`~/.quaid/.installer.lock`) remaining.

## Common failure modes

- **Installer hang during OC plugin provision** — npm postinstall stalls; historically ~2h on first
  run but succeeds. Node_modules persists across kill+retry.
- **Matrix channel hang on OC startup** — if `openclaw onboard` hangs at "resolving authentication →
  starting...", re-onboard with `--skip-channels` and inject matrix config from the existing synapse
  access_token post-onboard. Baked into the `quaid-livetest-base` snapshot.
- **Compatibility circuit breaker degraded** — if `quaid doctor` reports compat degraded, check
  `core/compatibility.py` version detection resolves the OC semver (57c59d914 hardened this; older
  builds may mis-parse).

## Post-M0 coordinator steps (before M1)

Coordinator applies per-platform livetest overrides (`enableExtractionBufferLog`,
`chunk_tokens=1500`) — see `COORDINATOR.SKILL.md` "Post-first-M0: Livetest Config Overrides
(per-platform)". Do NOT write `inactivityTimeoutMinutes` globally; it flips per-platform only around
M4.
