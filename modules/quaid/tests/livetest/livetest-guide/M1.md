# M1: Extraction

Purpose: validate that Quaid extracts facts from a session regardless of which trigger fires. All three extraction paths must work.

This milestone has three parts — run all three. A failure in any part is an M1 failure.

## Pass (all parts)

- Each trigger stores the seeded fact in the instance `memory.db`.
- DB / FTS check finds the distinctive keyword after the trigger completes.
- No cross-trigger bleed (a `/new` pass should not also be what extracted the content meant for the timeout pass).

## Part A — Lifecycle-triggered extraction (`/new`, `/reset`, `/clear`, `/compact`)

Each platform has its own set of lifecycle commands; run the ones its lane supports:

| Trigger | OC | CC | CDX |
| --- | --- | --- | --- |
| `/new` | yes (Matrix DM) | yes | yes |
| `/reset` | yes (Matrix DM) | — | yes |
| `/clear` | — | yes (`/clear` replaces `/reset` on CC) | — |
| `/compact` | yes | yes | — |

Procedure, per trigger:

1. Send the agent a memorable fact in natural conversation. Use a distinctive keyword in each fact so you can disambiguate which pass stored what.
   - Example seed: "My neighbour just won a regional chili cook-off with a smoked brisket recipe she's kept secret for twenty years."
   - Note the distinctive token you'll search for (e.g. `chili cook-off`, `brisket`).
2. Wait for the agent to fully acknowledge. OC via `matrix-read`; CC/CDX in the visible pane.
3. Fire the trigger. See platform supplement for the exact command shape.
4. Wait for extraction.
   - OC extracts **inline** on the trigger, ~30–60 s after `/new` or `/reset`.
   - CC extracts **asynchronously** via `session_end` after `/exit` or `/clear`; wait **at least 2 minutes** before checking.
   - CDX extracts via rollout + session-transition hooks after the next lifecycle signal; wait ~2 min.
5. Verify the fact is in the DB. FTS direct check is the primary verification — `quaid recall-fast` is vector-only and misses nonsense keywords.

   ```bash
   ssh REMOTE_HOST 'sqlite3 ~/.quaid/instances/<INSTANCE>/data/memory.db \
     "SELECT rowid, name FROM nodes_fts WHERE nodes_fts MATCH '\''<keyword>'\'' LIMIT 3;"'
   ```

   A natural-language `quaid recall "<query>"` is also valid if recall is healthy.

Hook trace markers to confirm lifecycle detection (vary by adapter):

- **OC (2026.3.13+):** `hook.message.command_detected` (command=new|reset|compact) → `daemon.signal_written` (type=reset|compaction).
- **CC:** `hook.session.ended` on `/exit`, `hook.session.cleared` on `/clear`.
- **CDX:** `hook.session.transition` on `/new`.

## Part B — Rolling extraction (chunk_tokens threshold)

Rolling extraction fires mid-session when the sanitized transcript buffer hits `capture.chunk_tokens`. In livetest that's 1500 tokens per the post-M0 config. Do not confuse the `context_emitted` length (pre-sanitization) with the buffer that drives rolling — check `semantic_buffer_tokens` in the per-session rolling state file under `~/.quaid/instances/<INSTANCE>/data/rolling-extraction/<SESSION_ID>.json`.

Procedure:

1. Hold a multi-turn conversation (5–10 turns) feeding the agent varied facts until `semantic_buffer_tokens` passes the threshold.
2. Watch the daemon log (`~/.quaid/instances/<INSTANCE>/logs/daemon.log`) for a `rolling_flush` event with `signal_type=rolling` and `final_facts_stored > 0`.
3. Verify the first half of the conversation's facts are in the DB while the conversation is still alive (rolling extracted them mid-session).

Pass: at least one rolling_flush fires before the session ends, and the stored facts are a subset of what you fed the agent before the flush.

## Part C — Timeout extraction (idle)

Timeout extraction fires after `capture.inactivityTimeoutMinutes` of idle. Default is 60 minutes — livetest flips it to `1` for M1 Part C on the **one platform** running this part, then restores `60` after. See `COORDINATOR.SKILL.md` "M4 idle-timeout flip — per platform" (naming unchanged from legacy layout) for the flip/restore procedure.

Procedure:

1. Coordinator flips `capture.inactivityTimeoutMinutes=1` on the platform's config; restarts the lane's extraction daemon.
2. Send the agent a memorable fact. Agent acknowledges.
3. Stop interacting with the agent and do not fire any lifecycle trigger.
4. Wait ~80 seconds for the idle timer to elapse + daemon scan.
5. Verify via daemon log: `signal_type=timeout`, `final_facts_stored > 0`.
6. Check DB with the same FTS query pattern as Part A.
7. Coordinator restores `capture.inactivityTimeoutMinutes=60`; restarts the daemon.

Pass: the fact stores through the timeout path with no lifecycle trigger involved.

## Common PWN vs FAIL notes

- Tester had to press an extra Enter / restart a lane TUI / work around a CDX input quirk → PWN-note, not FAIL.
- Extraction fired via a different trigger than the one being tested (e.g. timeout fired before `/new` landed) → PWN-note on that part; note which path actually fired.
- Hook throws an unhandled exception instead of emitting empty context and bailing cleanly → FAIL.
- DB never receives the fact through any path → FAIL.
