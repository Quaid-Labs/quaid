# M2: Recall

Purpose: validate that Quaid's recall paths find stored facts correctly. Covers every recall surface
— auto-inject, deliberate, graph traversal, and date-range — as parts of one milestone. Failing any
part is an M2 failure; PASS requires all.

Depends on M1 having stored a verifiable seed set.

## Pass (all parts)

- Auto-inject surfaces top-ranked matches **without** the agent calling `quaid recall` explicitly
  (Part A).
- Explicit `quaid recall` returns the right memory for a targeted query (Part B).
- Graph recall follows stored edges and returns rows reachable via traversal, not just direct nodes
  (Part C).
- Date-bounded recall returns in-window rows and excludes out-of-window rows (Part D). The
  off-by-one guard is mandatory.

## Part A — Auto-inject

Tests that hook pre-inject surfaces relevant memory in the agent's context without the agent needing
to make an explicit recall tool call. Per design, pre-inject has a **hard 3 s budget**; its LLM
pre-planner bails at 2 s. If pre-inject misses or returns weak rows, the agent falling back to
explicit `quaid recall` is the intended fallback path, not a failure of this part.

Procedure:

1. Seed a fact relevant to the question you will ask — e.g. "Baxter is a golden retriever who loves
   tennis balls."
2. Wait for extraction (via M1 Part A triggers).
3. In a fresh session boundary, ask the agent a natural question about the seeded topic ("What do
   you know about Baxter?").
4. Check:
   - Hook trace: `hook.inject.recall_done` has non-zero `count` within the 3 s budget, no unhandled
     `hook.inject.recall_error`.
   - The agent answers from injected context (visible in the pre-prompt block) — no explicit `quaid
     recall` tool call.
5. If the agent DID fall back to explicit recall and still answered correctly, that's PWN-note, not
   FAIL.

## Part B — Deliberate recall

Tests that explicit `quaid recall <query>` returns expected rows.

Procedure:

1. Using an M1-stored fact, run:
   ```bash
   ssh REMOTE_HOST 'quaid recall "<natural query>" --limit 5'
   ```
2. Verify the stored fact is in the top results with reasonable similarity (≥0.6 for exact-anchor
   queries).

Pass: the seeded fact appears in top rows for queries that should match it.

## Part C — Graph traversal

Tests that graph-aware recall traverses stored edges. Requires a fact that, through extraction,
produced a graph edge (e.g. a relation like `friend_of`, `pet_of`).

Procedure:

1. Seed a fact with an explicit relationship: "My neighbour Nessa owns a golden retriever named
   Baxter."
2. After extraction, verify the edge landed:
   ```bash
   ssh REMOTE_HOST 'sqlite3 ~/.quaid/instances/<INSTANCE>/data/memory.db \
     "SELECT subject, relation, object FROM edges WHERE subject LIKE '\''%Nessa%'\'' OR object LIKE '\''%Nessa%'\'';"'
   ```
3. Ask a question that requires graph traversal to answer — e.g. "Who owns Baxter?" (requires
   following the `pet_of` edge).
4. Check recall / injection returns the Nessa → Baxter relationship, not just the raw Baxter fact.

Pass: graph-aware recall returns traversed rows with correct direction. Stored direction must match
rendered direction (no inbound-edge flipping).

## Part D — Date-range recall

Tests that recall honors `date_from`, `date_to`, `as_of`, and aliases like `before`, `since`,
`until`, `after`, `asOf`.

**Mandatory off-by-one guard** before any positive `date_to` probe: derive the evidence date from
the stored row, not from wall-clock. Guessed cutoffs produce false failures.

Memory matrix:

```bash
# no bounds — should include all
ssh REMOTE_HOST 'quaid recall "<query>"'

# date_to at old date — should exclude rows newer than old date
ssh REMOTE_HOST 'quaid recall "<query>" '\''{"date_to":"YYYY-MM-DD"}'\'''

# as_of = date_to alias
ssh REMOTE_HOST 'quaid recall "<query>" '\''{"as_of":"YYYY-MM-DD"}'\'''

# date_from at new date — should exclude rows older than new date
ssh REMOTE_HOST 'quaid recall "<query>" '\''{"date_from":"YYYY-MM-DD"}'\'''

# closed range old..new
ssh REMOTE_HOST 'quaid recall "<query>" '\''{"date_from":"YYYY-MM-DD","date_to":"YYYY-MM-DD"}'\'''
```

Alias spot checks: `before`, `since` must behave like `date_to`, `date_from`. If canonical keys pass
but an alias fails, PWN not FAIL.

Docs-date probes (project-docs recall, `stores=["docs"]`) additionally require:

- Evidence comes from `PROJECT.log` dated rows, never from current `PROJECT.md` boilerplate.
- No warning-only fallback ("Date-bounded docs recall requires DocsRAG date_from/date_to support")
  when matching PROJECT.log chunks exist.
- `project status` / `project diff` for managed projects without a `source_root` must exit `0` (no
  fatal "no source_root" error).

## PWN vs FAIL

- Auto-inject missed but explicit recall picked it up → PWN-note (intended fallback).
- Alias-only failure while canonical date keys work → PWN-note.
- Pending rows rank below approved rows — this is **intended policy**, not a bug. Do not report as
  M2 FAIL.
- Date-bounded docs recall returns wrong-window rows → FAIL.
- Explicit recall never returns a correctly-seeded, correctly-extracted row → FAIL.
- Recall raises an unhandled exception (TimeoutError, RuntimeError) instead of bailing with
  partial/empty rows → FAIL.
