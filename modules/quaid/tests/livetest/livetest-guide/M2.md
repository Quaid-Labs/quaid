# M2: Extraction

Purpose: validate that Quaid extracts facts from a session regardless of which
trigger fires. All three extraction paths must work.

This milestone has three parts — run all three. A failure in any part is an M2
failure.

## Shared seed: rolling transcript

All three parts feed from `data/rolling-transcript.md`, the canonical two-
chunk non-actionable user monologue. Chunk 1 is ~1400 tokens (below the
`chunk_tokens=1500` threshold — rolling does not fire yet). Chunk 2 adds
enough margin that the cumulative sanitized buffer lands safely above the
threshold across CC/OC/CDX tokenization variance, so rolling fires between
chunks. Both chunks carry an ACK-only prefix so the agent replies with just
`ACK` and does not burn time composing content replies.

Per-platform send mechanics (Matrix for OC, visible pane for CC/CDX) are
documented in your platform supplement.

## Pass (all parts)

- Each trigger stores expected facts in the instance `memory.db`.
- DB / FTS check finds the distinctive keyword after the trigger completes.
- No cross-trigger bleed — a fact seeded for the `/new` pass should not be
  attributed only to the later rolling flush (and vice versa).

## Part A — Lifecycle-triggered extraction

Every platform has a lifecycle command that closes a session. Your platform
supplement lists the exact commands supported for your lane. Run the ones your
lane supports; if your lane only supports one lifecycle command, run one pass.

Procedure, per trigger your lane supports:

1. Send Turn 1 of `data/rolling-transcript.md`. Wait for the agent to
   acknowledge.
2. Fire the lifecycle trigger exactly as described in the platform supplement.
   For CDX, `/new` is only the boundary command; send the first real prompt in
   the new session before checking rollout/session-transition evidence.
3. Wait the extraction window described in your platform supplement (the time
   from trigger → fact-in-DB varies per platform).
4. Verify the fact is in the DB. FTS direct check is the primary verification:

   ```bash
   ssh REMOTE_HOST "sqlite3 \$HOME/.quaid/instances/\$INSTANCE/data/memory.db \
     \"SELECT rowid, name FROM nodes_fts WHERE nodes_fts MATCH 'Niseko' LIMIT 3;\""
   ```

   A natural-language `quaid recall "<query>"` is a valid secondary check if
   recall is healthy.

Hook trace markers vary by platform — see your supplement for the exact line
you should look for in `$SILO/logs/daemon/*.log`.

## Part B — Rolling extraction (chunk_tokens threshold)

Rolling extraction fires mid-session when the sanitized transcript buffer
hits the configured threshold (`chunk_tokens=1500` in livetest config).

The canonical seed is `data/rolling-transcript.md`. It is designed so the
test is exactly two sends plus one lifecycle trigger:

- Chunk 1 (~1400 tokens) puts the buffer below threshold — rolling does
  NOT fire yet.
- Chunk 2 crosses threshold with margin across CC/OC/CDX tokenization —
  rolling fires between chunks.
- A lifecycle trigger after Chunk 2 flushes the residual Chunk 2 tail via
  session_end extraction.

Both chunks carry the ACK-only prefix from `rolling-transcript.md` so the
agent replies with just `ACK`.

Procedure:

1. Send Chunk 1 (prefix + Chunk 1 body) via the platform supplement's send
   mechanism.
2. Wait for the agent's `ACK` reply.
3. Before Chunk 2, sanity-check that rolling has NOT fired yet:

   ```bash
   ssh REMOTE_HOST "tail -50 \$SILO/logs/daemon/extraction-daemon.log \
     | grep -c rolling_flush"
   ```

   Expect: 0. If >= 1, the threshold is set below 1400 or the chunk ran
   long — PWN-note and continue.

   If the daemon log shows `gained non-internal content past a frozen internal
   cursor` after Chunk 1, continue with Chunk 2 instead of treating the
   recovery as a lifecycle flush. The recovered Chunk-1 tail is expected to stay
   in rolling state while the transcript is active, then cross the normal
   rolling threshold when Chunk 2 arrives. An `internal_cursor_unfrozen_flush`
   before Chunk 2 is only acceptable after the transcript has gone quiet for
   the rolling internal-cursor grace window; during the active two-chunk test it
   is a product bug.

4. Send Chunk 2 (prefix + Chunk 2 body).
5. Wait for the agent's `ACK` reply, then pause ~15 s for the daemon to
   process. Look for rolling progress / success:

   ```bash
   ssh REMOTE_HOST "tail -80 \$SILO/logs/daemon/extraction-daemon.log \
     | grep -E 'rolling_flush|rolling_batch|semantic_buffer_tokens'"
   ```

   Expect: a `rolling_flush` entry with `semantic_buffer_tokens` ≥ 1500
   right before the flush.

6. Fire the lane's `LIFECYCLE` command (from your platform supplement) to
   flush the residual via session_end extraction.
   For CDX, follow `/new` with the first real prompt in the new session before
   verifying rollout/session-transition evidence.
7. Wait the lane's post-lifecycle extraction window (see platform
   supplement).
   For CDX Part B, do not stop at the first post-Chunk-2 `rolling_flush`.
   CDX often publishes the threshold-crossing rolling payload first, then
   publishes the Chunk-2 residual facts through a later `session_end` flush.
   Poll up to 7 minutes for a `rolling_flush` row for the test session with
   `processing_signal_type=session_end` before declaring Chunk-2-only markers
   missing.
8. Verify keywords from both chunks land in the DB:

   ```bash
   # Chunk-1 keywords (should land via rolling)
   for kw in "Niseko" "Kinesis Advantage360" "Pilot Custom 74" "Phoebe Bridgers"; do
     ssh REMOTE_HOST "sqlite3 ~/.quaid/instances/\$INSTANCE/data/memory.db \
       \"SELECT COUNT(*) FROM nodes_fts WHERE nodes_fts MATCH '$kw';\""
   done
   # Chunk-2-only keywords (should land via lifecycle)
   for kw in "Baxter" "orange linen notebook" "Emília Rosa"; do
     ssh REMOTE_HOST "sqlite3 ~/.quaid/instances/\$INSTANCE/data/memory.db \
       \"SELECT COUNT(*) FROM nodes_fts WHERE nodes_fts MATCH '$kw';\""
   done
   ```

Pass:

- A `rolling_flush` event appears in the daemon log between Chunks 1 and 2.
- Chunk-1 keywords (`Niseko`, `Kinesis Advantage360`, `Pilot Custom 74`,
  `Phoebe Bridgers`) each return ≥ 1 row.
- Chunk-2-only keywords (`Baxter`, `orange linen notebook`, `Emília Rosa`) each
  return ≥ 1 row after the `LIFECYCLE` flush completes.
- Both paths are exercised in one test run.

### Anti-pattern: forcing residual rolling tails to flush early

The "Chunk 2 missing after rolling stage" symptom is not automatically a
product bug. Rolling extraction may leave subthreshold semantic content in the
rolling snapshot; the next real lifecycle (`session_end`, `/clear`, `/compact`,
or the lane's equivalent boundary) drains that residual tail.

Do not patch the daemon to write a synthetic `session_end` just to make the
residual tail appear sooner. That is an async-tightening fix: cure worse than
disease. Wait the documented async window before classifying Chunk-2-only
markers as missing. This follows the memory rules
`feedback_settle_window_is_platform_hook_gap_not_bug.md` and
`feedback_pwn_egregiousness_bar.md`: extraction that takes multiple poll cycles
is normal behavior, not a PWN by itself.

Exception: a frozen internal-cursor recovery must not fire a synthetic
`session_end` while the transcript is still active. The daemon may use
`internal_cursor_unfrozen_flush` only after the transcript is quiet and the
recovered semantic buffer is still below the rolling threshold.

## Part C — Timeout extraction

Timeout extraction fires after `capture.inactivityTimeoutMinutes` of idle time.
Default is `60`; livetest flips it to `1` on the lane running this part, then
restores `60` after. The tester owns the flip/restore — coordinator does not
do it for you.

**Important**: the timeout *starts* extraction. It does not *finish* extraction
by itself. Once the timeout fires for a session, that session is queued for
extraction. If older idle sessions are already in the timeout queue ahead of
yours, they get extracted first and your session waits behind them. This has
shown up across runs as "timeout fired but my fact didn't store within 90s."
The fix is to drain the queue before flipping the timeout, so your test
session is the only thing the timeout extraction has to process.

Procedure:

1. **Drain the existing timeout/lifecycle queue** so prior idle sessions don't
   consume the timeout slot first:

   ```bash
   ssh REMOTE_HOST "QUAID_INSTANCE=\$INSTANCE \$QCLI daemon flush"
   ```

   Expect rc=0 with a summary of what was processed. Queue is empty after.

2. Flip the timeout to `1` on your lane's platform config:

   **Important**: do not flip `capture.inactivity_timeout_minutes=1` until
   Part B's lifecycle flush is fully complete and Chunk-2-only keywords are
   confirmed in the DB. Setting the 1-minute timeout early risks a premature
   `session_end` between content dumps if the tester pauses for more than a
   minute between Part B chunks.

   ```bash
   ssh REMOTE_HOST "QUAID_INSTANCE=\$INSTANCE python3 - <<'PY'
import json
import os
from pathlib import Path
p = Path.home() / '.quaid' / 'instances' / os.environ['QUAID_INSTANCE'] / 'config.json'
data = json.loads(p.read_text())
data.pop('inactivity_timeout_minutes', None)
data.setdefault('capture', {})['inactivity_timeout_minutes'] = 1
p.write_text(json.dumps(data, indent=2) + '\n')
PY"
   ```

   Restart the platform service per your platform supplement so the new value
   takes effect.

3. Start a fresh session. Send one short turn seeding a distinctive fact:

   > Just logging: my garden shed combination is written inside an indigo glass lantern.

4. Wait for the agent to acknowledge. **Do not send another turn.**
5. Idle until the 1-minute timeout fires *and* extraction completes. With the
   queue drained in step 1, this is normally well under 90 s. If your seed
   doesn't land within 2 min, it's a real product issue, not queue ordering.
6. Verify the fact landed in DB via FTS (`"indigo glass lantern"`).
7. Restore the timeout:

   ```bash
   ssh REMOTE_HOST "QUAID_INSTANCE=\$INSTANCE python3 - <<'PY'
import json
import os
from pathlib import Path
p = Path.home() / '.quaid' / 'instances' / os.environ['QUAID_INSTANCE'] / 'config.json'
data = json.loads(p.read_text())
data.pop('inactivity_timeout_minutes', None)
data.setdefault('capture', {})['inactivity_timeout_minutes'] = 60
p.write_text(json.dumps(data, indent=2) + '\n')
PY"
   ```

Pass: the fact stores through the timeout path with no lifecycle trigger
involvement.

## Common PWN vs FAIL notes

- Tester had to press an extra Enter / restart a platform TUI / work around an
  input quirk → PWN-note, not FAIL.
- Extraction fired via a different trigger than the one being tested (e.g.
  timeout fired before `/new` landed) → PWN-note; note which path actually
  fired.
- Hook throws an unhandled exception instead of emitting empty context and
  bailing cleanly → FAIL.
- DB never receives the expected keywords through any path → FAIL.
