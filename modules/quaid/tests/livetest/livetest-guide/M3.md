# M3: Recall

Purpose: validate that Quaid's recall paths find stored facts correctly. Covers
every recall surface — auto-inject, deliberate, graph traversal, and date-range
— as parts of one milestone. Failing any part is an M3 failure; PASS requires
all.

Depends on M2 having populated `memory.db` from the rolling transcript.

## Shared seed: historical rows

Part D (date-range) needs dated rows that span a wider window than the rolling
transcript naturally provides. Before Part D starts, inject the canonical
historical set with:

```bash
ssh REMOTE_HOST "INSTANCE=\$INSTANCE \
  ~/quaidcode/dev/modules/quaid/tests/livetest/livetest-guide/data/seed-historical.sh"
```

This adds 7 approved rows spanning 2023-Q1 through 2024-Q4, each with a
distinctive keyword (`hist-amber-valentine-2023`, `hist-ironwood-workshop-2023`,
`hist-meridian-summit-2023`, `hist-jasper-retreat-2024`, `hist-cobalt-release-2024`,
`hist-sepia-reading-2024`, `hist-carbon-audit-2024`).

## Pass (all parts)

- Auto-inject surfaces top-ranked matches without the agent calling
  `quaid recall` explicitly (Part A). Crucially: even if the agent also issues
  an explicit fallback recall, the hook must have **passed something back** —
  silent auto-inject misses on a recall-triggering turn are a FAIL.
- Explicit `quaid recall` returns the right memory for a targeted query
  (Part B).
- Graph recall follows stored edges and returns rows reachable via multi-hop
  traversal (Part C).
- Date-bounded recall returns in-window rows and excludes out-of-window rows
  (Part D). Off-by-one guard is mandatory.

## Part A — Auto-inject

Tests that hook pre-inject surfaces relevant memory in the agent's context
without the agent making an explicit recall tool call. Pre-inject has a hard
3 s budget; its LLM pre-planner bails at 2 s.

**Signal requirement.** The pre-inject path must produce observable positive
evidence that something was returned — check `$SILO/logs/daemon/preinject.jsonl`
(or equivalent per your platform supplement) for an entry with a non-empty
`injected` payload on the turn being tested. If pre-inject fires and returns
empty, that's a miss and the agent's fallback to explicit recall is the
intended safety net — in that case the milestone is PWN-note, not PASS.

Procedure:

1. Start a fresh session after M2's rolling-extraction flush landed (so facts
   from the transcript are in the DB).
2. Ask a question that leans on a specific extracted fact — e.g.
   "What grinder do I use for my espresso setup?"
3. Before the agent answers, check `preinject.jsonl` on disk for the current
   turn's entry. It must have a non-empty `injected` array referencing the
   Baratza Encore fact.
4. Observe the agent's answer. PASS if the agent answers correctly without
   issuing its own `quaid recall` tool call.
5. If the agent did fall back to explicit recall AND pre-inject produced
   non-empty injected payload AND the agent still answered correctly, that's
   PWN-note.

## Part B — Deliberate recall

Tests that explicit `quaid recall <query>` returns expected rows.

Procedure:

1. From the tester shell, issue recall for a known keyword from the rolling
   transcript:

   ```bash
   ssh REMOTE_HOST "\$QCLI recall 'Niseko'"
   ssh REMOTE_HOST "\$QCLI recall 'Pilot Custom 74'"
   ```

2. The top row in each recall must match the correct fact — not a loosely
   adjacent one.

Pass: both recalls return the expected fact in the top 3 rows.

## Part C — Graph multi-hop

Tests that graph-aware recall traverses stored edges. The rolling transcript
seeds an explicit multi-hop family tree:

```
Solomon → Yuni → Kai → Mei
Solomon → Leah → Nathan
Solomon → Leah → Iris
```

Procedure:

1. After extraction, verify the direct edges landed:

   ```bash
   ssh REMOTE_HOST "sqlite3 \$HOME/.quaid/instances/\$INSTANCE/data/memory.db \
     'SELECT source_id, target_id, relation FROM edges WHERE source_id LIKE \"%solomon%\" \
      OR source_id LIKE \"%yuni%\" OR source_id LIKE \"%leah%\" LIMIT 20;'"
   ```

2. Issue a multi-hop recall via the agent or CLI:

   ```bash
   ssh REMOTE_HOST "\$QCLI recall 'what does my partner\\'s brother do' --debug"
   ```

   Expect: Kai's boatbuilding-studio fact returned via 3-edge traversal
   (`Solomon Steadman --spouse_of--> Yuni --sibling_of--> Kai --has_fact--> "Yuni's brother Kai works at a small boatbuilding studio"`).

Pass: the 3-edge recall returns Kai's boatbuilding fact; the answer cites
the traversal in `--debug` output (graph_path with all 3 edges visible).

**Note on test depth:** multi-hop graph tests must stay at 2–3 edges of
depth. A previous version of this section asked a 4-edge query
("what does my partner's brother's wife do" → Mei ceramics), which is
unrealistic — real users decompose deeper questions across turns. If
facts are in the DB but the recall ranking layer doesn't surface them at
4+ hops, that is an LLM-grounding limitation, not a Quaid recall break.
Keep this milestone at ≤3 edges so it tests the recall layer rather than
the LLM reasoning ceiling.

## Part D — Date-range recall

Tests that recall honors `date_from`, `date_to`, `as_of`, and aliases like
`before`, `since`, `until`, `after`, `asOf`.

Run the historical seed first (see "Shared seed" above).

Probes:

| Probe              | Config                                              | Must return         | Must NOT return     |
| ------------------ | --------------------------------------------------- | ------------------- | ------------------- |
| P1: 2023 only      | `{"date_from":"2023-01-01","date_to":"2023-12-31"}` | `hist-*-2023`       | `hist-*-2024`       |
| P2: 2024 only      | `{"date_from":"2024-01-01","date_to":"2024-12-31"}` | `hist-*-2024`       | `hist-*-2023`       |
| P3: as_of mid-2024 | `{"as_of":"2024-06-30"}`                            | `hist-jasper-*`     | `hist-sepia-*`      |
| P4: after mid-2024 | `{"after":"2024-06-30"}`                            | `hist-sepia-*`      | `hist-jasper-*`     |

Invoke each probe:

```bash
ssh REMOTE_HOST "\$QCLI recall 'hist' '{\"date_from\":\"2023-01-01\",\"date_to\":\"2023-12-31\"}'"
```

**Off-by-one guard:** a row with `created_at='2024-01-01T00:00:00Z'` must NOT
appear in the 2023 probe (P1) even though some adjacent boundary logic would
include it. If it appears, that's a FAIL for Part D.

Alias spot checks: `before`, `since` must behave like `date_to`, `date_from`.
If the canonical keys pass but an alias fails, PWN-note, not FAIL.

## Part E — Source-chunk recall

Tests that recall correctly attaches bounded source-chunk evidence when the
caller opts in via `include_chunks`, omits it by default, and defends against
owner-scoped integrity violations.

Depends on M2 having populated `source_chunks` from rolling extraction (each
extracted fact links to the chunk it was distilled from via `nodes.source_chunk_id`).

### Probe E1 — Default omits chunks

```bash
ssh REMOTE_HOST "\$QCLI recall 'umeboshi onigiri' --json" \
  | python3 -c "import json,sys; r=json.load(sys.stdin); rows=r.get('results',r) if isinstance(r,dict) else r; \
print('rows=', len(rows), 'first source_chunk=', rows[0].get('source_chunk') if rows else None)"
```

Pass: rows returned, every row has `source_chunk` either absent or `None`.
A `source_chunk` dict appearing without `include_chunks=true` is a FAIL
(silent payload bloat regression).

### Probe E2 — Opt-in returns bounded chunks

```bash
ssh REMOTE_HOST "\$QCLI recall 'umeboshi onigiri' \
  '{\"include_chunks\":true,\"max_chunk_tokens\":100}' --json"
```

Pass requirements:

- At least the top row has a `source_chunk` dict with non-empty `text`.
- `text` token-budget honored — should be roughly ≤ 100 tokens
  (~400-600 chars). A chunk of several thousand tokens unbudgeted is FAIL.
- `chunk_id` on the dict matches `source_chunk_id` on the row.
- The recall meta block contains `meta.source_chunks.attached >= 1` and
  `meta.source_chunks.failed == false`.

### Probe E3 — Owner-mismatch defense (destructive, must restore)

Tests that the integrity check intercepts a chunk whose `owner_id` does not
match the recall row's `owner_id`. This validates the cross-owner safety
defense added in the source-chunks lineage.

**Procedure (must run with cleanup):**

```bash
# 1. Pick a chunk_id from a row that include_chunks recall returns.
CHUNK=$(ssh REMOTE_HOST "\$QCLI recall 'umeboshi onigiri' \
  '{\"include_chunks\":true,\"max_chunk_tokens\":100}' --json 2>/dev/null" \
  | python3 -c "import json,sys; r=json.load(sys.stdin); rows=r.get('results',r) if isinstance(r,dict) else r; \
print(rows[0]['source_chunk_id'])")
echo "test chunk: $CHUNK"

# 2. Capture original owner so it can be restored.
ORIG_OWNER=$(ssh REMOTE_HOST "sqlite3 \$HOME/.quaid/instances/\$INSTANCE/data/memory.db \
  \"SELECT owner_id FROM source_chunks WHERE chunk_id='$CHUNK'\"")
echo "orig owner: $ORIG_OWNER"

# 3. Mutate to a foreign owner.
ssh REMOTE_HOST "sqlite3 \$HOME/.quaid/instances/\$INSTANCE/data/memory.db \
  \"UPDATE source_chunks SET owner_id='intruder-owner' WHERE chunk_id='$CHUNK'\""

# 4. Re-run include_chunks recall and capture stderr separately.
ssh REMOTE_HOST "\$QCLI recall 'umeboshi onigiri' \
  '{\"include_chunks\":true,\"max_chunk_tokens\":100}' --json" \
  > /tmp/m3e-defense-stdout 2> /tmp/m3e-defense-stderr

# 5. Restore IMMEDIATELY (do this even if recall raised).
ssh REMOTE_HOST "sqlite3 \$HOME/.quaid/instances/\$INSTANCE/data/memory.db \
  \"UPDATE source_chunks SET owner_id='$ORIG_OWNER' WHERE chunk_id='$CHUNK'\""
```

Pass requirements depend on the runtime `fail_hard` setting in
`shared/config/global/config.json` (`retrieval.fail_hard`):

- **`fail_hard=true` (livetest default):**
  - stderr contains `RuntimeError: Recall result references missing source chunk: <chunk_id>`
    OR `Recall result source chunk owner mismatch: ...`.
  - stdout is empty / non-JSON (process raised).
  - The integrity violation surfaced loudly. PASS.
- **`fail_hard=false`:**
  - Recall returns JSON with rows; the row tied to the mutated chunk has
    `source_chunk_missing: true` and no `source_chunk` dict.
  - Daemon log contains `[recall] include_chunks owner mismatch for result ... chunk <chunk_id>`
    (or `owner missing` variant).
  - `meta.source_chunks.missing >= 1`. PASS.

A silent attach of the foreign-owner chunk (chunk dict returned, no warning,
no raise) is FAIL — defense bypassed. A crash that does not reference the
chunk_id (generic exception, no warning text) is also FAIL.

**Cleanup verification:** after restore, re-run probe E2 and confirm the
chunk attaches normally again. Skipping cleanup leaves the silo poisoned
for downstream milestones.

## Common PWN vs FAIL notes

- Pre-inject fires with empty injected payload and agent falls back to explicit
  recall → PWN-note, not FAIL.
- Pre-inject never fires at all on a recall-triggering turn → FAIL.
- Graph recall returns only direct edges (no multi-hop traversal) → FAIL.
- Off-by-one boundary violation in Part D → FAIL.
- Alias fails but canonical key passes → PWN-note.
- `source_chunk` present without `include_chunks=true` (Part E1) → FAIL.
- `source_chunk.text` ignores `max_chunk_tokens` budget (Part E2) → FAIL.
- Owner-mismatch defense bypassed — foreign-owner chunk attached silently
  (Part E3) → FAIL.
- Test left chunk with mutated owner (E3 cleanup skipped) → FAIL (poisons
  downstream milestones).
