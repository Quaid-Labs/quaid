# M5: Silo Isolation

Purpose: validate that memory is silo'd at the right scope. Two agents on the
**same instance** share one memory pool (by design); two **different instances**
on the same host have fully separated silos. Part A tests that sharing works;
Part B tests that separation works.

## Pass (both parts)

- Part A: two agent sessions on the **same instance** see each other's
  extracted facts. They share the instance's memory pool by design; if a fact
  seeded in session X is invisible to session Y, the silo is broken in the
  wrong direction.
- Part B: two **different instances** on the same host (same `QUAID_HOME` root
  but different instance dirs) have fully separated `memory.db`, signal queues,
  and project directories. No row written in one instance's silo appears in
  the other's recall.
- Unlinking a project from one instance does not remove it from the other;
  deleting is global (affects every instance that shares the project).

## Part A — Shared memory across sessions within one instance

1. Start Session X in the lane's normal pane. Seed a distinctive fact:

   > My Friday pumpkin seed ritual is roasting the seeds with smoked paprika
   > and maple salt.

2. End Session X (`LIFECYCLE` command per platform supplement), then force the
   daemon to drain the lifecycle extraction before starting Session Y. This seed
   is intentionally small and may not cross the rolling threshold, so verifying
   before lifecycle/session-end races the async extractor.

   ```bash
   ssh REMOTE_HOST "QUAID_INSTANCE=\$INSTANCE \$QCLI daemon flush"
   ```

   Verify the fact landed:

   ```bash
   ssh REMOTE_HOST "\$QCLI recall 'Friday pumpkin seed ritual'"
   ```

3. Start Session Y in the same pane, same instance. Ask naturally:

   > What's my Friday ritual?

   CDX note: `/new` may show a welcome screen/resume hint. That is not the
   verification point. Send the Session Y recall prompt, apply the documented
   bare-Enter retry if it is staged but not submitted, then verify the new
   rollout/session transition.

4. The agent must surface the Friday pumpkin seed ritual. Extraction from Session X
   contaminated Session Y's recall context by design — that's the shared-pool
   property this part exercises.

Pass: Session Y recalls the fact; both sessions see the same memory pool.

## Part B — Separation across instances on the same host

Part B requires a second instance on the same host as the lane under test.
Creating a second instance is platform-specific — your platform supplement
documents the exact mechanism (for example, a second CC instance is created
by launching CC from a different project dir; OC has a dedicated second-agent
creation path; CDX uses a different `QUAID_INSTANCE` env var).

**IMPORTANT — silo provisioning timing**: Quaid silos are provisioned on the
first **hook call** by the agent, NOT at registration / `agents add` /
config-time creation. This is core Quaid architecture. So after `openclaw
agents add <name>`, the silo will NOT yet exist under `~/.quaid/instances/`.
The silo is created when the first agent invocation fires its hook (e.g.
`openclaw agent --agent <name> --message ...`). Only then is `quaid
instances list` expected to show the new sibling. Treat the gap between
`agents add` and first invocation as expected behavior, not a bug.

OpenClaw `agents add` diagnosis: the add command can load the Quaid plugin at
CLI startup, but it should not invoke Quaid's `before_agent_start` or
`before_prompt_build` hooks. If `agents add` times out, immediately run
`openclaw agents list` and inspect the hook trace. If the agent appears in
`agents list` and no hook invocation was running for that add command, classify
the add step as an OpenClaw CLI completion hang and proceed to the first
hook-bearing invocation. If Quaid hook trace shows a stuck hook during `agents
add`, route to W1 as a Quaid hook regression with the trace window. Do not leave
the lane as generic INCONCLUSIVE.

OpenClaw note: the first sibling invocation can fail with gateway close 1008
`pairing required` if the OC device/node asks for broader scopes than its
current pairing token allows. That is OC gateway pairing state, not Quaid silo
provisioning. Drain/approve pending OC device or node scope upgrades through
the supported `openclaw devices` / `openclaw nodes` CLI path, then retry the
first hook-bearing sibling invocation. Do not edit OC pairing JSON by hand.
If the OC `devices list` / `devices approve` commands themselves keep creating
new `scope upgrade pending approval` request IDs, stop the retry loop and mark
the OC sibling lane as an external-platform pairing deadlock. Quaid has already
done its part if the sibling appears in `quaid instances list --json` after the
first hook-bearing invocation. Mark the OC sibling sub-test
inconclusive/platform-blocked and report the OC version plus the sequence of
request IDs seen to the coordinator.

Open the second instance in a new split-pane window inside the `livetest`
tmux session. Kill the split-pane at the end of the test.

1. Confirm both instances exist:

   ```bash
   ssh REMOTE_HOST "\$QCLI instances list --json"
   ```

2. Generate a lane-unique marker, then seed it in instance X:

   ```bash
   LANE_TAG="$(printf '%s' "${PLATFORM:-$INSTANCE_X}" | tr -cd '[:alnum:]' | tr '[:upper:]' '[:lower:]')"
   M5_ISOLATION_MARKER="m5b${LANE_TAG}x$(date -u +%Y%m%d%H%M%S)"
   echo "The reading chair for this instance has marker $M5_ISOLATION_MARKER beside its celadon desk lamp."
   ```

   Send that exact sentence to instance X.

   Do not reuse `brass` or other common words as the isolation assertion.
   Earlier milestones intentionally seed legitimate facts containing `brass`
   into the main instance, so broad keyword absence is not a valid separation
   check once a lane has real run history.

3. Wait for extraction on X. Verify in X:

   ```bash
   ssh REMOTE_HOST "QUAID_INSTANCE=\$INSTANCE_X \$QCLI recall '$M5_ISOLATION_MARKER reading chair'"
   ```

4. Attempt the same recall against instance Y:

   ```bash
   ssh REMOTE_HOST "QUAID_INSTANCE=\$INSTANCE_Y \$QCLI recall '$M5_ISOLATION_MARKER reading chair'"
   ```

5. Instance Y's recall must not surface the marker or the seeded reading-chair
   fact. Y may return unrelated rows from its own silo; unrelated rows are not
   a FAIL. This part tests that X's exact seeded fact does not cross into Y,
   not that Y is empty.

6. Confirm at the DB level that the row exists in X's silo only:

   ```bash
   ssh REMOTE_HOST "sqlite3 ~/.quaid/instances/\$INSTANCE_X/data/memory.db \
     \"SELECT COUNT(*) FROM nodes_fts WHERE nodes_fts MATCH '$M5_ISOLATION_MARKER';\""
   ssh REMOTE_HOST "sqlite3 ~/.quaid/instances/\$INSTANCE_Y/data/memory.db \
     \"SELECT COUNT(*) FROM nodes_fts WHERE nodes_fts MATCH '$M5_ISOLATION_MARKER';\""
   ```

   Expect: X returns ≥ 1, Y returns 0.

7. **Unlink-isolation check.** Unlink a project from X (use
   `quaid project unlink`, not `delete` — unlink removes the project's
   association with one instance; delete removes it globally). Verify Y still
   sees the project if it was previously shared:

   ```bash
   ssh REMOTE_HOST "QUAID_INSTANCE=\$INSTANCE_X \$QCLI project unlink <name>"
   ssh REMOTE_HOST "QUAID_INSTANCE=\$INSTANCE_Y \$QCLI project list | grep <name>"
   ```

   Expect: X's `project list` no longer shows `<name>`, but Y still does.

8. Kill the second-instance split-pane.

Pass: extraction from X never appears in Y's recall; unlink is per-instance;
delete is global.
