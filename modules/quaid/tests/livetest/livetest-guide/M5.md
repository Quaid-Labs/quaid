# M5: Silo Isolation (Multi-Agent + Multi-Instance)

Purpose: validate that different agent sessions and different instances don't bleed memory into each other. Old M12 (multi-agent within one instance) and M13 (multi-instance separation) were near-identical scaffolding exercising the same isolation property at different scopes. One milestone with two parts.

## Pass (both parts)

- Part A: two agent sessions on the **same instance** see only the appropriate slice of shared memory; owner-scoped facts stay owner-scoped; extraction from one session does not contaminate the other's recall.
- Part B: two **different instances** (e.g. OC `openclaw-main` vs a CDX `codex-*` instance) have fully separated memory.db, signal queues, and project directories. No row written in one instance's silo appears in the other's recall.
- Deleting an instance (or its associated misc project) removes its silo without cross-impacting the other.

## Part A — Multi-agent within one instance

Covers the case where the same owner has two concurrent sessions with the same instance.

1. Open a second session with the platform under test (for OC: second Matrix DM session or second agent window; for CC: second `/tmp/cc-livetest` workspace; for CDX: second codex TUI with the same project dir).
2. In **session A**, seed an owner-level fact: "My favorite hot drink is oolong tea."
3. In **session B** (same instance, same owner), seed a different fact: "I walk the Lantern Sluice path on Saturdays."
4. Wait for both sessions' extractions (M1-style triggers).
5. In session A, ask about session B's fact. In session B, ask about session A's fact.
6. Verify:
   - Both facts are in the instance's memory.db (single silo owns both).
   - Recall surfaces the right fact when the other session asks about it (owner-level facts are shared).
   - Session-ID-scoped fields (e.g. session-specific snippets, pending-notification rows) are not leaking across session IDs.

Pass: both facts recallable, session-scoped state remains scoped to its session.

## Part B — Multi-instance separation

Covers the case where two DIFFERENT instances share the same host (same `QUAID_HOME` root but different instance dirs).

1. Confirm you have at least two instances on the host:
   ```bash
   ssh REMOTE_HOST 'quaid instances list --json'
   ```
2. Seed a distinct fact in **instance X** (e.g. OC): "Instance-X secret marker: tamarind lantern 0423."
3. Wait for X's extraction.
4. In **instance Y** (e.g. CDX), do recall with an explicit query that would match X's marker:
   ```bash
   ssh REMOTE_HOST 'QUAID_INSTANCE=<Y_INSTANCE_ID> quaid recall "tamarind lantern" --limit 5'
   ```
5. Verify Y returns zero rows for X's marker.
6. Reverse the test: seed a Y-only fact, confirm X cannot recall it.
7. DB-level cross-check — each instance has its own `memory.db`:
   ```bash
   ssh REMOTE_HOST 'sqlite3 ~/.quaid/instances/<X>/data/memory.db \
     "SELECT COUNT(*) FROM nodes_fts WHERE nodes_fts MATCH '\''tamarind'\'';"'
   ssh REMOTE_HOST 'sqlite3 ~/.quaid/instances/<Y>/data/memory.db \
     "SELECT COUNT(*) FROM nodes_fts WHERE nodes_fts MATCH '\''tamarind'\'';"'
   ```
   The marker row exists in X only.
8. **Delete-isolation check.** Delete a misc project associated with X (use `quaid project delete <misc-name>`). Verify Y's silo is unaffected (`quaid instances list` still shows Y, Y's memory.db intact, Y's workers alive).

## Scope variants per platform

- **OC:** instance is `openclaw-main` and is fixed. Additional OC instances are rare in the livetest; Part B often uses OC ↔ CDX or OC ↔ CC.
- **CC:** instance is derived from the project dir path (`/tmp/cc-livetest` → `claude-code-private-tmp-cc-livetest`). Run Part A with two different `claude` sessions in the same `/tmp/cc-livetest` dir (same instance). Run Part B with a CC session in a different dir (e.g. `/tmp/cc-m13-test` → `claude-code-private-tmp-cc-m13-test`).
- **CDX:** same dir-derivation rule. Run Part B with `/private/tmp/cdx-livetest` vs `/private/tmp/cdx-m13-test`.

## PWN vs FAIL

- Additional instance setup required tester workarounds (CDX extra-Enter, path deviation from the legacy guide) → PWN-note.
- A stray row in Y's DB that came from X but is clearly residual from a prior test run (not the new seed) → PWN-note, clean and re-run.
- Owner-level fact from X is surfaced in Y's recall (cross-instance bleed) → FAIL.
- Deleting X resurrects after a sync cycle → FAIL.
- `quaid instances list` is missing a live instance → FAIL.
