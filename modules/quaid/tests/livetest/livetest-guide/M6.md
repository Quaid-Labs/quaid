# M6: Agent Notifications (Deferred + Provider Outage)

Purpose: validate that Quaid surfaces notifications back to the agent via the hook-inject path —
both scheduled/deferred notices and fast-path provider-outage errors. Old M14 (deferred notification
surfacing) and M15 (provider outage fast path) share the same injection surface; combined into one
milestone with two parts.

## Pass (both parts)

- Part A: a deferred notice (janitor-queued or coordinator-queued) appears in the next turn's
  injected context; a dedupe turn does not repeat the same notice.
- Part B: an unreachable LLM provider triggers a provider-error notification that surfaces **on
  every turn where the broken recall/LLM call actually fires**, with no dedupe/throttle suppressing
  actively-firing errors.

## Part A — Deferred notification surfacing

**Design intent:** janitor and other slow background systems write deferred notices intended for the
next time the operator is actually conversing with the agent. Drain on turn boundary is explicit —
deferred notices never auto-drain during autonomous/hook-only paths.

Procedure:

1. Confirm no pending deferred notice:
   ```bash
   ssh REMOTE_HOST 'quaid notify --deferred-status'
   ```
   Expect: `pending=0` (or no pending lines).
2. Queue a deferred notice (coordinator writes to the delayed-LLM-requests JSON path):
   ```bash
   ssh REMOTE_HOST 'python3 -c "
import json, os, time
p = os.path.expanduser(\"~/.quaid/instances/<INSTANCE>/.runtime/notes/delayed-llm-requests.json\")
os.makedirs(os.path.dirname(p), exist_ok=True)
data = json.load(open(p)) if os.path.exists(p) else {\"requests\": []}
data[\"requests\"].append({
    \"id\": \"m6-partA-<timestamp>\",
    \"status\": \"pending\",
    \"kind\": \"janitor_notice\",
    \"message\": \"M6 test notice: scheduled review found 3 facts that may be outdated and need refresh.\"
})
json.dump(data, open(p, \"w\"), indent=2)
print(\"queued\")
"'
   ```
3. Confirm pending:
   ```bash
   ssh REMOTE_HOST 'quaid notify --deferred-status'
   ```
   Expect: `pending=1`.
4. Send a natural user turn ("Hey, what is up?") through the platform's visible interaction surface.
5. Verify the notice appears in the agent's context and the agent's reply acknowledges it in plain
   language.
6. Check the JSON row for the notice: `status=delivered` with `delivered_at` populated.
7. **Dedupe turn:** send "Ready for the next check." Agent should reply ready and NOT repeat the
   notice.
8. Confirm `pending=0` again.

## Part B — Provider outage fast-path

**Design intent:** provider errors are critical user-facing failures ("your LLM is broken"). They
must NOT be deduped/throttled **for turns where the error actually fires**. If the error fires on
this turn, it must surface. Contrast: janitor summaries are deduped (Part A) because janitor fires
once per night so the class naturally de-dups itself.

Procedure (Variant A — key removal, preferred if a real provider was used in M0):

1. Remove the Quaid shared auth credential:
   ```bash
   ssh REMOTE_HOST 'mv ~/.quaid/shared/auth/credentials.json ~/.quaid/shared/auth/credentials.json.m6-backup'
   ```
2. Send a user turn that requires an LLM call (recall triggering deep reasoning, or extraction-path
   turn).
3. Verify the provider error message appears in the agent's injected context that turn.
4. Send a second identical turn. Verify the error fires AGAIN, not suppressed.
5. Send a third turn. Still fires — no dedupe.
6. Restore the credential:
   ```bash
   ssh REMOTE_HOST 'mv ~/.quaid/shared/auth/credentials.json.m6-backup ~/.quaid/shared/auth/credentials.json'
   ```
7. Verify clean recovery on the next turn (no provider-error notice injected, normal recall
   behavior).

Variant B (if Variant A is not possible for a given platform) — temporarily point the instance's
models config at a non-existent model name to force 404 errors. Restore the default model afterward.

## PWN vs FAIL

- Part A dedupe turn still has the notice but phrased differently — PWN if the system clearly
  attempted dedup; FAIL if the dedupe logic is totally absent.
- Part B error notice fires only on the first turn then disappears while config is still broken —
  FAIL (dedupe of actively-firing error is the explicit anti-pattern).
- Cross-session bleed (Part A notice intended for session X appears in session Y) — FAIL.
- On restore (Part B step 7), the agent still shows provider-error injected content — FAIL; means
  restore didn't clear.
