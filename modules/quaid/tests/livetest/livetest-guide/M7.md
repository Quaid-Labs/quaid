# M7: System Context Refresh on Lifecycle

Verifies that runtime-evolved system context — project list, agent identity
file evolution, edits to system-context markdown — is picked up by the next
compaction-class lifecycle event, without requiring a full `/new`.

## Why this matters

Long-lived sessions span weeks. Things change: new projects appear, agent
identity files (`SOUL.md`, `USER.md`, `ENVIRONMENT.md`) evolve, system-context
markdown gets edited. Without a refresh hook, an agent in a long session
would never see those updates. Auto-inject via memory recall does not cover
this — system context is its own injection layer.

## Trigger

The default refresh trigger is the lane's compaction-class lifecycle event.
The exact command name varies per platform; your platform supplement lists
the command and any alternative (some platforms lack a compaction hook and
use a different boundary entirely).

## Procedure

1. Start a fresh session and exchange a few normal turns so initial system
   context is loaded.

2. From your side (do NOT ask the agent to do this — the agent should not be
   aware of the canary), edit the instance system context markdown to insert
   a unique canary fact. Identity files live in the VISIBLE home
   (`~/quaid/instances/<INSTANCE>/`), not the hidden home (`~/.quaid/...`).
   Append to all three identity files so whichever one the platform's
   system-context loader reads will pick it up:

   ```bash
   for f in SOUL.md USER.md ENVIRONMENT.md; do
     ssh REMOTE_HOST "printf '\\nThe office plant is named Bartholomew. It is a fiddle-leaf fig.\\n' >> ~/quaid/instances/\$INSTANCE/\$f"
   done
   ```

3. Trigger the lane's refresh lifecycle command per the platform supplement.
   CDX note: `/new` may show a welcome screen/resume hint; this is normal. Send
   the canary question as the first real prompt in the new session, use the CDX
   bare-Enter retry if the prompt is staged but not submitted, and only then
   verify rollout/session-transition evidence. If no new rollout file appears
   after the follow-up prompt submitted, restart Codex in the pane before
   retrying.

4. Wait ~30 s for compaction and the next user turn to be processed. CC
   refreshes by rebuilding split `.claude/rules/quaid-*.md` files. Because
   Claude Code may not reload those files after `/compact` until a new session,
   Quaid also emits a one-shot, identity-only compact refresh bridge on the
   next turn. This bridge must stay small and must not include normal recall or
   docs context.

5. Send a fresh prompt that depends on the canary, **without referencing
   memory or recall**:

   > What's the office plant named?

   The agent's response to this turn IS the test signal. Do not grade from
   logs alone.

6. Verify the agent answers `Bartholomew` (or quotes the canary fact
   directly) from the refreshed system context.

7. **If the agent fails step 6** (says it doesn't know, or cannot find a plant
   name), send the byte-search diagnostic prompt **on the very next turn,
   before any cleanup**:

   > Without reading any external files, search your current context for any
   > mention of the name Bartholomew, can you find it?

   This forces the agent to enumerate what it can actually see right now. The
   answer disambiguates two failure modes:
   - **Agent says yes, Bartholomew is in my context** → the refreshed rules
     files or one-shot identity bridge reached model-visible context, but the
     agent's grounding ignored it on the original M7 question. Quaid's context
     refresh path is working; bug is in the model's grounding behavior.
   - **Agent says no, Bartholomew is not in my current context** → the refreshed
     split rules files and one-shot identity bridge did not reach model-visible
     context. Capture the response and route to W1 with the `quaid-user.md`,
     `quaid-soul.md`, `quaid-environment.md`, and hook trace contents.

   Capture the agent's literal response to this prompt as part of the M7
   verdict.

## Pass

- Agent answers `Bartholomew` / `fiddle-leaf fig` from the refreshed system
  context.
- Agent did NOT invoke `quaid recall` or any memory tool to retrieve the
  answer — system context refresh is a separate path from memory recall.

## Fail

- Agent has no knowledge of the canary fact (system context did not refresh).
- Agent only finds the canary by invoking `quaid recall` (means the canary
  was extracted to memory but system context still didn't refresh — partial
  credit at best, PWN-note).
- On byte-search diagnostic (step 7), agent says it cannot find Bartholomew
  in its current context — strong signal that neither the refreshed split rules
  files nor the one-shot identity bridge reached model-visible context. Capture
  the response and route to W1.

## Cleanup

After PASS, remove the canary everywhere it can propagate so it does not pollute
later milestones, the post-test audit, or GLOBAL janitor review. The canary may
also exist in the session transcript because identity context was injected into
model-visible turns. Do not edit or delete transcripts; they are run evidence.
Instead, drain pending extraction first, then clean the mutable derived state.

1. Drain queued extraction work and confirm no signal files remain:

   ```bash
   ssh REMOTE_HOST "QUAID_INSTANCE=\$INSTANCE \$QCLI daemon flush --timeout 180"
   ssh REMOTE_HOST "find ~/.quaid/instances/\$INSTANCE/data/extraction-signals -type f 2>/dev/null | sort"
   ```

   Expect: `daemon flush: status=drained` and the `find` command prints no
   files. If signals remain or flush does not drain, stop and preserve the
   output. Do not run cleanup while a transcript flush can still recreate the
   canary.

2. Remove source identity lines, derived visible-home snippets, and any memory
   nodes that already captured the temporary canary:

   ```bash
   ssh REMOTE_HOST "python3 ~/quaidcode/dev/modules/quaid/tests/livetest/scripts/cleanup-m7-canary.py --instance \$INSTANCE"
   ```

   Expect: command exits `0` and prints `M7 canary cleanup complete` with
   `removed_lines` and `deleted_nodes` counts. A `deleted_nodes=0` result is
   valid only when extraction never stored the canary.

3. Wait one short extraction window, then verify without mutating. This catches
   transcript-backed re-extraction that lands after the point-in-time cleanup:

   ```bash
   ssh REMOTE_HOST "sleep 120; python3 ~/quaidcode/dev/modules/quaid/tests/livetest/scripts/cleanup-m7-canary.py --instance \$INSTANCE --verify-only"
   ```

   Expect: command exits `0` and prints `M7 canary cleanup verification clean`.
   If it fails, route the output as INFRA evidence, drain again, and rerun the
   cleanup from step 1.

If the helper fails, stop and preserve the output. Do not proceed to later
milestones until a follow-up sweep confirms:

```bash
ssh REMOTE_HOST "! grep -R 'Bartholomew' ~/quaid/instances/\$INSTANCE 2>/dev/null"
ssh REMOTE_HOST "sqlite3 ~/.quaid/instances/\$INSTANCE/data/memory.db \
  \"SELECT COUNT(*) FROM nodes WHERE name LIKE '%Bartholomew%';\""
```

Expect: the grep exits `0` because `! grep` found nothing, and the sqlite count
is `0`.
